# GitHub 项目参考

桌面的 **GitHub** 应用收录供人和 Agent 设计产品、实现功能时查阅的项目参考。

## 文件、版本与专题

每个仓库维护一篇 `content/github/<slug>.md`。本栏目另保留 `topics` 作为专题入口。文章自动列入 `/github/`，互链使用 `/github/<slug>/`，配图放在旁边的 `./assets/<slug>/`。列表展示文章的 `description`，摘要用读者遇到的具体问题说明这篇文章能帮助做什么决定。

在 `sources` 中至少用一条记录同时给出公开仓库地址 `url` 和所读版本 `revision`，例如提交哈希或发行标签。用文档、源码或测试为关键判断提供可核对的依据，区分长期适用的设计原则、所读版本的实现细节和自己的推断。私有笔记及环境记录留在研究工作区。

在 `topics` 填入至少一个 GitHub 专题 ID，先选文章能回答的主要设计问题。正文有一段可独立参考的机制时，可以再选一个专题。例如 DeepSeek Harness 既讲工具如何接入运行时，也具体追踪了事件日志如何恢复会话，可以同时归入这两个专题。GitHub 专题用 `title` 命名领域，用 `description` 说明读者能在这里比较什么。有项目归入后，专题会出现在 `/github/topics/`，每个项目始终使用原来的文章直链。[维护专题](../content-workflow.md#维护专题)

## 解释项目的设计

主文要让第一次接触项目的人能向同事解释整个项目怎么运转，以及作者为什么这样设计。开篇说明谁会用它、从哪个入口发起操作，以及最终得到什么结果。先画清主要组件的分工和完整的输入输出路径，再选一个能把关键机制串起来的场景。例如写 Agent 框架，先交代网页、SDK 和批处理各自如何接入、共用哪些运行时组件，再用一次报告生成解释模型如何调用工具、会话如何接续。换掉案例之后，这张架构图仍应成立。

在关键设计处讲清两件事。第一，项目需要同时满足哪些要求，更直接的实现会在哪个具体情形下失效？第二，项目用什么数据、判断或执行顺序解决了它，又留下什么代价？作者在设计记录、提案或提交说明中交代过动机时，引用其中的原始问题，再用源码或测试核对现在的实现。只有实现证据时，可以说明这种做法带来的效果，若进一步推断作者的动机，需写清依据。对存储系统，可以追踪并发写入时依据哪个版本作判断。对图形库，可以跟随一个坐标跨过渲染和导出。对内容工具，可以比较脚本能检出的缺陷与仍需人判断的缺陷。具体机制决定章节和篇幅。

## 架构图与时序图

每篇正文都用 Mermaid 绘制以下两种图，组件名称与正文保持一致。

- **全局架构图**用 `flowchart` 画出使用方、项目和外部依赖的边界。对照上游的入口、公共接口和设计文档，找齐决定项目如何运转的主要模块。节点写清职责，箭头写明传递的调用、数据或产物。在图上标出谁持有状态、谁作出关键决定、结果交给谁。按项目自身的形态画图，例如插件要画宿主何时调用它，生成工具要画产物由谁消费。总图太密时，保留各模块及跨模块关系，把模块内部的机制另画一张详图，沿用总图中的名称。
- **核心组件时序图**用 `sequenceDiagram` 追踪一个真实用例。以参与交互的组件或对象为 `participant`，从触发动作画到可观察的结果，标清调用、返回或异步交付的先后。重试、拒绝或故障恢复会改变结果时，画出相应分支。

## 审阅与更新

审稿时先单读总图，从真实入口沿箭头追到结果，检查图上能否看出项目最重要的一项设计取舍。例如客户端重连后，哪一端仍持有恢复所需的数据？再改动案例中的一个条件，让审阅者依据正文预测结果，并指出决定结果的那条规则。例如，模型已经根据旧工具说明发出调用，这时卸载再注册同名工具，旧调用会落到哪个实现？

再换一个产品需求，检查读者能否选出值得借鉴的设计，说清成立的前提，判断何时更简单的实现就够用。若正文只能回答原案例，回到源码补齐推理中缺的那一步。上游改变了适用条件、组件边界或交互方式时，更新原文、受影响的图和出处。
