# Blog 文章

## 文件与专题

博客文章默认存为 `content/blog/<slug>.md`。需要分类时使用 `content/blog/<category>/<slug>.md`，分类目录保留一层，`topics/` 专用于专题定义。两种位置的公开直链都是 `/blog/<slug>/`，博文互链使用这条路径。`topics` 和 `page` 保留给专题与分页。配图放在文章旁的 `./assets/<slug>/`，用相对路径引用。

分类目录用于组织源文件。`kind` 可填 `article` 或 `note`。站点按 frontmatter 的 `topics` 收录专题，至少填写一个 `content/blog/topics/` 下已建专题的文件名，去掉 `.md` 后缀。一篇文章可关联多个专题，一个专题也可收录多篇文章。[维护专题](../content-workflow.md#维护专题)

## 博客原文读解

1. 阅读正文，核对作者、标题和所读版本。遇到社交平台的引介帖，循原帖找到长文。原站正文打不开时，可以通过原帖的作者、标题和版本信息核对全文镜像，并在 `sources` 保留原文及镜像链接。只有摘要或节选时，交代已读范围，把结论限定在可核对的内容。关键主张要回看支撑它的段落、图表或代码，转述的重要案例和数据尽量追到一手出处。
2. 用提纲记下原文要回答的问题、主要主张、证据和适用条件。全篇读解成稿后对照原文逐项回查，确认各阶段、步骤或清单项在稿中有落点。相近内容可以合并，保留会影响结论的限制、反例和取舍。聚焦部分论点时，在开头交代范围。
3. 从原文的具体问题或案例开篇，按读者理解这些判断所需的顺序展开。每节说明作者的做法如何起作用、依赖哪些条件。尽量沿用同一个案例，让前一步的结果接到下一步。调整章节顺序时，保留原文主张和证据的对应关系。
4. 写清数字来自谁，区分实测记录、示例估算和自己的推算。交代单位和统计时段，比例或前后对比标出分母或基线。能复算时给出算式或表格，缺少关键口径时说明。比较成本或效率时，同时核对任务产出、质量或时延是否可比。把数字的出处放在对应段落末。
5. 推演要交代案例的起点、关键判断和动作，标明原文给出的条件与为推演添加的假设。写清什么结果算完成、查哪条记录能确认。如果例外或中途失败会改变结论，说明如何判断当前状态、从哪一步继续。适合动手的主题可以换一个输入做练习，交代读者如何核对自己的结果。

## 移动博客文章

当一个长期主类已经积累多篇文章，单独浏览这组源稿会更方便时，再加一级分类目录。

先用 `pnpm content:move <slug> <category>` 预览移动路径，再用 `pnpm content:move <slug> <category> --apply` 执行。工具会把 Markdown 文件和该文的 `assets/<slug>/` 一起移到目标分类。

执行后用 `git status --short` 和 `git diff` 核对变更，运行 `pnpm build`，并预览文章原直链和配图。

如果移动进程被强制终止，先用 `git status --short` 检查源目录和目标目录的 Markdown 与配图，把它们恢复为一份完整的文章。确认原进程已退出后，用 `rmdir content/blog/.move-post-<slug>` 清除残留的空锁目录，再重试。
