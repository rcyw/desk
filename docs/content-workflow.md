# 内容工作流

按要交付的内容选择下表中的指南。写稿时先查找已有稿件、核对来源，成稿后按「审阅与发布」交付。同一条 GitHub 发布说明，用来补充今天的 AI Brief 时按日报归期，用来更新项目参考时按仓库版本核对实现。

| 这次要做的事 | 指南 |
| --- | --- |
| 写博客、读解一篇原文，或移动已有博文及配图 | [Blog 文章](content-workflow/blog.md) |
| 为一个仓库建立或更新项目参考 | [GitHub 项目参考](content-workflow/github.md) |
| 阅读论文并在 Papers 写作或更新读解 | [Papers 论文读解](content-workflow/papers.md) |
| 整理可复制的提示词，或更新已有模板 | [Prompts 模板](content-workflow/prompts.md) |
| 编写或增补一期 AI Brief 日报、博客周报 | [按日期整理时讯](content-workflow/briefs.md) |
| 新建或调整 Blog、Papers 或 GitHub 专题 | [维护专题](#维护专题) |

## 建立或更新稿件

1. 确定主题、来源和交付方式。按整理目标、来源和 `slug` 查找已有稿件与任务 PR。有对应的 PR 时，先看现有差异和审阅意见，再继续工作。同一个问题优先更新原文，有独立阅读价值的主题另起一篇。目标和来源版本均已处理时，报告本次无需改动。
2. 核对公开稿的来源、版本和关键结论。区分来源陈述、自己的判断和待确认事项。资料访问不全时，写明缺口，把结论限定在可核对的范围。在 `sources` 中记录可公开的原始出处，优先链接到具体版本，版本可核实时填写 `revision`。
3. 按指南选择文件位置。用 `slug` 命名的稿件采用能辨认主题的英文短语，例如 `kubernetes-ai-native-stack.md`。去掉小写的 `.md` 后缀就是 `slug`，在本栏目内须唯一，只含小写字母和数字，词间用短横线连接。`index.md` 是保留文件名，`assets/` 用于配图。固定前缀留给定期更新的系列。
4. 新稿用 `publishedAt` 记录站点显示的首发日期，合并前确认。即使填写未来日期，稿件也会随合并后的部署公开。实质更新填写 `updatedAt`，保留原文件名、公开路径和首发日期。各栏目的必填字段和允许值见[内容定义](../src/content.config.ts)。

技术长文从具体问题或任务切入，逐步解释机制、边界和取舍。交代读懂结论所需的背景、前提和证据。关键术语、缩写、示例编号和指标首次出现时，说明其含义和用途。用来源和互链帮助读者核对出处与延伸阅读。

用 Mermaid 解释组件关系、交互顺序或状态变化。每张图回答一个明确的问题，放在读者需要它的段落。可以从多个视角展示同一组件，名称保持一致。图的种类和数量取决于稿件与栏目要求。

## 维护专题

Blog 和 Papers 共用 `content/topics/<id>.md`，GitHub 项目参考使用 `content/github/topics/<id>.md`。先在对应目录查找已有专题。新建时用小写字母、数字和短横线命名文件，稿件在 `topics` 中引用去掉 `.md` 的文件名。

用 `title` 命名专题，`description` 说明收录范围，`lang` 标明语言。`order` 填非负整数，数值小的排在前面。调整名称、说明或顺序时编辑原文件，已有稿件可继续使用原专题 ID。[专题字段定义](../src/content.config.ts)

## 审阅与发布

1. 在任务分支用 `pnpm dev` 本地预览稿件直链、相应的专题或日期归档入口、配图和 Mermaid。提交前格式化改动的文件并运行[仓库验证](../README.md#verification)。
2. 未完成或暂不宜公开的稿件留在本地或私有位置。构建会拒绝带 `draft` 字段的稿件。旧稿准备好公开后再移除该字段并提交。稿件可发布且已获授权时开普通 PR，写清整理目标、稿件路径、来源版本和验证结果，时讯附上统计窗口。需要提前征求公开意见时可用 GitHub Draft PR，完成后转为 Ready for review。公开仓库的 Draft PR 和分支源文件均可读。
3. CI 检查新增或修改的稿件能否生成可发布页面，为通过检查的就绪 PR 保留构建产物。按最终 diff 核对关键陈述的出处、工程推断和待验证结论。通读受影响的稿件，确认读者能仅凭正文说清问题、主要结论、依据和适用条件。正文或来源有实质变化时重新核对。
4. 审阅和 CI 通过后，维护者用 Squash and merge 合并到 `main`。在 `rcyw/desk` 启用 `PAGES_AUTO_PUBLISH` 时，最新的 `main` 提交通过推送 CI 后会自动触发 GitHub Pages 部署。[部署工作流](../.github/workflows/dispatch-pages.yml)

Bot 可根据审阅意见修稿、重跑检查并更新 PR。常规栏目如需自动合并，先约定来源、发布范围和独立审阅者，再让 GitHub 在必需的审阅和 CI 通过后执行合并。
