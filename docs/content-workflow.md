# 内容工作流

## 接收任务

确定主题、来源和交付方式。定期时讯还需系列名和统计窗口，时区默认为 `Asia/Shanghai`。迟跑和重跑均沿用该期窗口。

对公开稿核对来源、版本和正文里的关键结论。区分来源陈述、自己的判断和待确认事项。资料访问不全时，写明缺口，并保留有依据的结论。

## 建立或更新文章

1. 按整理目标、来源和 `slug` 查找已有文章与任务 PR。同一个问题更新原文，有独立阅读价值的主题另起一篇。同一期已有 PR 时，核对现有差异和审阅意见后续作。目标和来源版本均已处理时，报告本次无需改动。
2. 博客文章默认放在 `content/posts/<slug>.md`。整理有需要时使用 `content/posts/<category>/<slug>.md`，分类目录保留一层。GitHub 仓库参考放在 `content/github/<slug>.md`，见 [GitHub 项目参考](#github-项目参考)。论文读解见 [Papers 论文读解](#papers-论文读解)，日报见 [AI Brief 日报](#ai-brief-日报)。
3. 在 `sources` 记录可公开的原始出处，优先链接到具体版本。版本可核实时填写 `revision`。
4. 新稿用 `publishedAt` 记录站点显示的首发日期，合并前确认。填写未来日期的稿件也会随合并后的站点部署公开。实质更新填写 `updatedAt`，沿用原公开路径和首发日期。

## 文章格式

用能辨认主题的英文短语给文件命名，例如 `kubernetes-ai-native-stack.md`。去掉小写的 `.md` 后缀就是文章的 `slug`，整个文章集合内须唯一，使用小写字母或数字，用短横线分词。`index.md` 是保留文件名，`assets/` 用于存放配图。每个栏目有独立的文章路径，Blog 使用 `/posts/<slug>/`。发布后保留原文件名。固定前缀留给定期更新的系列。

Blog 的分类目录用于组织源文件。Frontmatter 的 `topics` 决定专题收录，一篇文章可关联多个专题，同一专题也可收录多篇文章。至少引用一个已建专题，填写 `content/topics/` 下对应文件名去掉 `.md` 后的 `slug`。博客文章互链用 `/posts/<slug>/`，配图放在该文章旁的 `./assets/<slug>/`，用相对路径引用。必填字段和允许值见 [内容定义](../src/content.config.ts)。

技术长文先给出一个具体问题或任务，再逐步解释关键机制、边界和取舍。正文要交代读懂主要结论所需的背景、前提和证据。支撑论点的术语、缩写、示例编号和指标首次出现时，说明它们的含义和用途。来源和互链供读者核对出处与延伸阅读。

积极用 Mermaid 展示组件关系、交互顺序和状态变化。每张图回答一个明确的问题，放在读者需要它的段落。同一组件可以从多个视角重复展示，名称保持一致，图数按理解需要决定。短时讯按内容需要配图。

### 移动博客文章

当一个长期主类已经积累多篇文章，单独浏览这组源稿会更方便时，再加一级分类目录。

先用 `pnpm content:move <slug> <category>` 预览移动路径，再用 `pnpm content:move <slug> <category> --apply` 执行。工具会把 Markdown 文件和该文的 `assets/<slug>/` 一起移到目标分类。

执行后用 `git status --short` 和 `git diff` 核对变更，运行 `pnpm build`，并预览文章原直链和配图。

如果移动进程被强制终止，先用 `git status --short` 检查源目录和目标目录的 Markdown 与配图，把它们恢复为一份完整的文章。确认原进程已退出后，用 `rmdir content/posts/.move-post-<slug>` 清除残留的空锁目录，再重试。

## GitHub 项目参考

桌面的 **GitHub** 应用收录供人和 Agent 设计产品、实现功能时查阅的项目参考。每个仓库维护一篇 `content/github/<slug>.md`，文件名使用小写字母、数字和短横线，`index` 和 `topics` 是保留名称。保存后自动列入 `/github/`，文章互链使用 `/github/<slug>/`，配图放在旁边的 `./assets/<slug>/`。列表展示文章的 `description`，摘要用读者遇到的具体问题说明这篇文章能帮助做什么决定。

在 `topics` 填入至少一个 GitHub 专题 ID，先选文章能回答的主要设计问题。正文有一段可独立参考的机制时，可以再选一个专题。例如 DeepSeek Harness 既讲工具如何接入运行时，也具体追踪了事件日志如何恢复会话，可以同时归入这两个专题。专题定义放在 `content/github/topics/<id>.md`，用 `title` 命名领域，用 `description` 说明读者能在这里比较什么，另填 `lang` 和 `order`。有项目归入后，专题会出现在 `/github/topics/`，每个项目始终使用原来的文章直链。

主文要让第一次接触项目的人能向同事解释整个项目怎么运转，以及作者为什么这样设计。开篇说明谁会用它、从哪个入口发起操作，以及最终得到什么结果。先画清主要组件的分工和完整的输入输出路径，再选一个能把关键机制串起来的场景。例如写 Agent 框架，先交代网页、SDK 和批处理各自如何接入、共用哪些运行时组件，再用一次报告生成解释模型如何调用工具、会话如何接续。换掉案例之后，这张架构图仍应成立。

在关键设计处讲清两件事。第一，项目需要同时满足哪些要求，更直接的实现会在哪个具体情形下失效？第二，项目用什么数据、判断或执行顺序解决了它，又留下什么代价？作者在设计记录、提案或提交说明中交代过动机时，引用其中的原始问题，再用源码或测试核对现在的实现。只有实现证据时，可以说明这种做法带来的效果，若进一步推断作者的动机，需写清依据。对存储系统，可以追踪并发写入时依据哪个版本作判断；对图形库，可以跟随一个坐标跨过渲染和导出；对内容工具，可以比较脚本能检出的缺陷与仍需人判断的缺陷。具体机制决定章节和篇幅。

每篇正文都用 Mermaid 绘制以下两种图，组件名称与正文保持一致。

- **全局架构图**用 `flowchart` 画出使用方、项目和外部依赖的边界。对照上游的入口、公共接口和设计文档，找齐决定项目如何运转的主要模块。节点写清职责，箭头写明传递的调用、数据或产物；在图上标出谁持有状态、谁作出关键决定、结果交给谁。按项目自身的形态画图，例如插件要画宿主何时调用它，生成工具要画产物由谁消费。总图太密时，保留各模块及跨模块关系，把模块内部的机制另画一张详图，沿用总图中的名称。
- **核心组件时序图**用 `sequenceDiagram` 追踪一个真实用例。以参与交互的组件或对象为 `participant`，从触发动作画到可观察的结果，标清调用、返回或异步交付的先后。重试、拒绝或故障恢复会改变结果时，画出相应分支。

审稿时先单读总图，从真实入口沿箭头追到结果，检查图上能否看出项目最重要的一项设计取舍。例如客户端重连后，哪一端仍持有恢复所需的数据？再改动案例中的一个条件，让审阅者依据正文预测结果，并指出决定结果的那条规则。例如，模型已经根据旧工具说明发出调用，这时卸载再注册同名工具，旧调用会落到哪个实现？再换一个产品需求，检查读者能否选出值得借鉴的设计，说清成立的前提，判断何时更简单的实现就够用。若正文只能回答原案例，回到源码补齐推理中缺的那一步。

在 `sources` 中至少用一条记录同时给出公开仓库地址 `url` 和所读版本 `revision`，例如提交哈希或发行标签。用文档、源码或测试为关键判断提供可核对的依据，区分长期适用的设计原则、所读版本的实现细节和作者推断。私有笔记及环境记录留在研究工作区。上游改变了适用条件、组件边界或交互方式时，更新原文、受影响的图和出处。

## 博客原文读解

1. 阅读正文，核对作者、标题和所读版本。遇到社交平台的引介帖，循原帖找到长文。原站正文打不开时，可以通过原帖的作者、标题和版本信息核对全文镜像，并在 `sources` 保留原文及镜像链接。只有摘要或节选时，交代已读范围，把结论限定在可核对的内容。关键主张要回看支撑它的段落、图表或代码，转述的重要案例和数据尽量追到一手出处。
2. 用提纲记下原文要回答的问题、主要主张、证据和适用条件。全篇读解成稿后对照原文逐项回查，确认各阶段、步骤或清单项在稿中有落点。相近内容可以合并，保留会影响结论的限制、反例和取舍。聚焦部分论点时，在开头交代范围。
3. 从原文的具体问题或案例开篇，按读者理解这些判断所需的顺序展开。每节说明作者的做法如何起作用、依赖哪些条件。尽量沿用同一个案例，让前一步的结果接到下一步。调整章节顺序时，保留原文主张和证据的对应关系。
4. 写清数字来自谁，区分实测记录、示例估算和自己的推算。交代单位和统计时段，比例或前后对比标出分母或基线。能复算时给出算式或表格，缺少关键口径时说明。比较成本或效率时，同时核对任务产出、质量或时延是否可比。把数字的出处放在对应段落末。
5. 推演要交代案例的起点、关键判断和动作，标明原文给出的条件与为推演添加的假设。写清什么结果算完成、查哪条记录能确认。如果例外或中途失败会改变结论，说明如何判断当前状态、从哪一步继续。适合动手的主题可以换一个输入做练习，交代读者如何核对自己的结果。

## Papers 论文读解

论文读解放在 `content/papers/<slug>.md`，每篇按文件名生成 `/papers/<slug>/`。文件名使用小写字母、数字和短横线，`index.md` 是保留文件名。`topics` 至少引用一个 `content/topics/` 中已建的专题。配图放在 `./assets/<slug>/`，用相对路径引用。

`title` 是读解标题。`paper.title` 填论文的原始标题，`paper.source` 填会议、期刊或预印本平台，`paper.url` 链接到所读的原文版本，`paper.version` 记录版本号或可核对的公开日期。原文有可定位的版本号时，使用该版本的链接和编号，例如 arXiv 的 `v2`。重读同一篇论文时更新原笔记，保留原文件名，并记录所读版本和 `updatedAt`。

从一个具体问题切入，交代论文要回答什么以及作者的主要主张。先解释理解方法所需的概念和假设，再用案例逐步解释核心设计和结果，指出证据来自哪些实验、图表或段落。最后讨论结论成立的条件、局限和应用场景，标清作者结论、自己的判断与已复现的结果。有助于理解时，用 Mermaid 展示关键机制。

## Prompts 模板

把同一使用场景的模板放在 `content/prompts/<slug>.md`，直链为 `/prompts/<slug>/`。沿用小写短横线文件名和共用出版字段，发布后保留原文件名。同一场景优先更新原文，适合单独分享或长期独立维护的模板才另建一篇。

每个独立用途用二级标题和一个顶层 `text` 围栏。保留原提示词的使用时机、动作、交付物和默认条件，只在确有需要时加参数。说明、可调项和出处放在围栏外，在 `sources` 记录原始出处。所附英文版可放进 `<details class="prompt-language" lang="en">`，用 `<summary>English</summary>` 和单独的 `text` 围栏提供独立复制。预览时逐条核对 `Copy Prompt` 得到的内容。

## 按日期整理时讯

- 每个系列每期一篇，同一期增补更新原文。通过博客发布的系列用包含频率的系列名加窗口起始日期作为 `slug`。
- 窗口计入起点，截止于终点。标题或正文开头标明覆盖日期。优先按事件发生时间归期，只有报道时间时注明报道时间。
- 选出窗口内有实质变化、能核实的事项。同一事件的多份报道合成一条，保留可核对的出处。短条目交代发生了什么、为什么值得关注和出处。没有足够的新材料时，报告本期无稿。

### AI Brief 日报

每期覆盖一个上海日历日，从当天 00:00 到次日 00:00 前。按覆盖日期存为 `content/briefs/YYYY/MM/YYYY-MM-DD.md`。文件日期的年、月须与上级目录对应，直链为 `/brief/YYYY-MM-DD/`。补跑、增补和校正都编辑该日的文件，`publishedAt` 记录实际首发日。配图放在日报旁的 `./assets/YYYY-MM-DD/`，用相对路径引用。

`description` 写该期摘要，可用 `highlights` 列出入口页的要点。正文每条资讯用一个小节交代变化、影响和原始出处。要点有实质更新时一并修订，并填写 `updatedAt`。

### 周报首发示例

上海时间 2026-11-09 00:00 至 2026-11-16 00:00 前的一期，存为 `content/posts/research-brief-weekly-2026-11-09.md`。示例引用已建的 `research-notes` 专题。

```yaml
---
title: 研究时讯 · 11 月 9 日至 15 日
description: 汇总本周值得跟进的变化和出处。
kind: note
lang: zh-CN
publishedAt: '2026-11-16'
topics:
  - research-notes
sources:
  - label: 项目版本说明
    url: https://example.com/project/releases/v1.2.0
    revision: v1.2.0
---
```

## 审阅与发布

1. 在任务分支用 `pnpm dev` 本地预览直链、专题或日期归档入口、配图和 Mermaid。未完成或暂不宜公开的稿件留在本地或私有位置。构建会拒绝带 `draft` 字段的稿件。旧稿准备好公开后，再移除该字段并提交。
2. 稿件可发布时开普通 PR，写清整理目标、文章路径、来源版本和验证结果，时讯附上统计窗口。需要提前征求公开意见时可用 GitHub Draft PR，完成后转为 Ready for review。公开仓库的 Draft PR 和分支源文件均可读。
3. CI 检查新增或修改的稿件能否生成可发布页面，并为通过检查的就绪 PR 保留构建产物。按最终 diff 核对关键陈述的出处、工程推断和待验证结论。通读受影响的文章，确认读者能仅凭正文说清讨论的问题、主要结论、依据和适用条件。正文或来源有实质变化时重新核对。
4. 审阅和 CI 通过后，维护者用 Squash and merge 合并到 `main`。在 `rcyw/desk`，合并提交通过 `main` 的 CI 后会自动触发 GitHub Pages 部署。

Bot 可根据审阅意见修稿、重跑检查并更新 PR。常规栏目如需自动合并，先约定来源、发布范围和独立审阅者，再让 GitHub 在必需的审阅和 CI 通过后执行合并。 [验证命令](../README.md#verification)
