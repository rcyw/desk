# 内容工作流

Agent 从任务提供的 Markdown、网页或代码仓库中提取结论，在 Desk 仓库里创建或更新可公开的整理稿。用这份约定处理研究笔记、独立文章和按日期整理的时讯。 [Markdown 格式](../README.md#写作) · [内容定义](../src/content.config.ts)

## 接收任务

先确定整理的主题、来源范围和交付方式。定期时讯还要确定系列名、统计窗口和时区。任务有明示约定时采用任务值，时区缺省采用 `Asia/Shanghai`。即使迟跑或重跑，也按该期安排的窗口收录。

对公开稿核对来源、版本和正文里的关键结论。区分来源陈述、自己的判断和待确认事项。资料访问不全时，写明缺口，并保留有依据的结论。

## 建立或更新文章

1. 按整理目标、来源和 `slug` 搜索已有文章与任务 PR。研究笔记继续回答同一个问题时，更新原文件。有独立阅读价值的主题另起一篇。相同来源版本和目标已经处理时，报告本次无需改动。
2. 把文章放在 `content/posts/<slug>/index.md`，配图随文章存放并用相对路径引用。优先复用已有专题。首篇需要新专题时，同时提交对应的 `content/topics/<slug>.md`，让读者看得出今后哪些内容会归入它。
3. 在 `sources` 写可公开的原始出处。优先使用可定位到具体版本的链接，在 `revision` 记录 commit、标签或文档版本。多篇资料支持同一个结论时，可以合写在一篇文章里并逐条列出来源。
4. 为新文章填写预计或确认的 `publishedAt`。首次公开时确认首发日期，实质更新用 `updatedAt`。保持原 `slug` 和首发日期，使已有链接和归档顺序可追溯。

## 按日期整理时讯

- 一个系列在一个时间窗口内对应一篇文章。用包含频率的系列名加窗口起始日期作为 `slug`，例如 `research-brief-weekly-2026-11-09`。同一期补充消息就更新这条路径。另一个频率用自己的系列名。
- 按时区解释窗口，计入起点，截止于终点。标题或正文开头标明覆盖日期。优先按事件发生时间归期，只有报道时间时注明报道时间。`publishedAt` 记录该篇首发日期。
- 选出窗口内有实质变化、能核实的事项。同一事件的多份报道合成一条，保留可核对的出处。短条目交代发生了什么、为什么值得关注和出处。没有足够的新材料时，报告本期无稿。

### 周报首发示例

上海时间 2026-11-09 00:00 起至 2026-11-16 00:00 前为一周。系列使用 `research-brief-weekly`，文章路径是 `content/posts/research-brief-weekly-2026-11-09/index.md`。假定该仓库已建 `research-notes` 专题，准备在 11 月 16 日首发。

```yaml
---
title: 研究时讯 · 11 月 9 日至 15 日
description: 汇总本周值得跟进的变化和出处。
kind: note
lang: zh-CN
publishedAt: '2026-11-16'
topics:
  - research-notes
sources:
  - label: 项目版本说明
    url: https://example.com/project/releases/v1.2.0
    revision: v1.2.0
---
```

## 预览和审阅

私密输入和待审稿留在本地或私有仓库。有 `draft: true` 的 Markdown 会从 Desk 页面排除。预览时在临时副本设置 `draft: false`，原稿保留草稿状态。公开仓库的分支和 PR 里的原文仍可读，提交前确认内容与配图适合公开。

按仓库的格式规则写 Markdown，用 Prettier 整理本次改动，运行与 CI 相同的验证命令，并预览生成的文章直链、专题入口和配图。准备 PR 时写明整理目标、文章路径、来源版本、时讯窗口、检查结果与待确认项。同一期已有任务 PR 时优先续作，先核对已有差异与审阅意见。合并由维护者决定，站点按获准的版本发布。 [本地验证命令](../README.md#本地开发)
